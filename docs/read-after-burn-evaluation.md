# 阅后即焚评估：多设备已读语义定义与实现/迁移成本（S3-07）

> **性质：仅评估，不写代码。** D1 已定：阅后即焚 = 发送后定时销毁
> （`SystemSettings.BurnAfterReadingMinutes`，默认 10 分钟），文案已改为
> “定时销毁”。本文只回答“如果将来 D1 改选已读销毁，要先定什么、要花多少”，
> 评估结论出来前不写任何实现代码。决定权在 Elan。

## 结论先行

- **建议保持 D1（定时销毁），不做已读销毁。** 单用户工具里发送者就是阅读者，
  已读销毁的实际收益面很窄（只覆盖“甲设备发、乙设备读”这一支），而成本是
  一套新的已读回执 + 设备归属判定。
- 如果将来改选：只做 **A 方案（任一设备已读即焚）+ 回退超时**；不要做 B/C
  （全读完才焚 / 按设备分别焚），因为它们需要一份设备清单，而设备清单本身
  的成本高于已读销毁的收益，且回退超时一加上就退化回定时销毁。
- 无论哪个方案，“已读”都必须有明确定义，且**发送设备自身的渲染不算已读**，
  否则消息会在发出的瞬间烧掉（见 §2.3）。

## 1. 多设备已读语义定义

### 1.1 三个候选语义

| 方案 | 定义 | 含义 |
|---|---|---|
| **A：任一设备已读即焚** | 任意一台已注册设备上报已读，消息立即对所有设备不可见 | “我读过了，它就没了”——最符合用户对阅后即焚的直觉 |
| **B：全部设备读完才焚** | 所有已注册设备都上报已读，消息才焚 | “每个设备都看过了才没” |
| **C：按设备分别焚** | 每台设备读后只在该设备上隐藏；服务端在所有设备读完（或回退超时）后删除 | 每台设备各自烧自己的副本 |

### 1.2 “已读”本身需要定义（四个候选事件）

| 候选事件 | 是否算已读 | 说明 |
|---|---|---|
| SignalR 推送到达（`ReceiveShareItem`） | 否 | 推送到达 ≠ 人看到了；手机锁屏时也会收到 |
| 消息在列表里渲染出来 | 否（文本消息尤其不能算） | 文本消息没有“详情页”，列表就是阅读面；滚动经过即渲染，误焚率极高 |
| 消息在视口内停留满 N 秒 / 用户点开查看 | 是（A 方案的推荐定义） | 文本：视口停留；文件：点开/下载（见 §1.3） |
| 文件被下载 | 是（文件消息） | 下载端点是一次明确的读取信号 |

### 1.3 单用户工具的特殊约束：发送设备不算

AnyDrop 是单用户工具，发送者与阅读者是同一个人。消息发出后会立刻渲染在
发送设备自己的列表里；如果“渲染即已读”，消息会在发出的瞬间烧掉。
因此任何方案都必须规定：**发送设备自身的查看不触发已读**（按发送时
记录的设备标识排除，或只统计“非发送设备”的已读回执）。
这也意味着已读销毁只对“甲设备发、乙设备读”这一支有意义——而这是少数流程，
不是主流程。这是建议保持 D1 的最主要理由。

### 1.4 回退超时是强制项

任何方案都必须配一个回退超时（例如沿用现有的 `BurnAfterReadingMinutes`）：
一台长期关机的设备不能让消息永远活着；一台已出售/重置的设备永远不会上报
已读。**回退超时一加上，已读销毁就退化为“定时销毁，但读过可以提前烧”**——
与 D1 的差别只剩“提前烧掉的那段时间”。

## 2. 现状盘点（2026-11-15，Stage 3 末）

| 现状 | 说明 | 对已读销毁的影响 |
|---|---|---|
| 定时销毁已实现 | `ExpiresAt = CreatedAt + BurnAfterReadingMinutes`；`ExpiredMessageCleanupService` 每分钟扫一轮，标记 `DeleteAfter = now + 7 天`（D5），广播 `ShareItemsDeleted`，行对所有读路径不可见，文件 7 天后物理删除 | 已读销毁可以复用同一条“标记不可见 + 广播 + 延迟物理删除”路径，不必另造删除通道 |
| **没有任何已读追踪** | 代码库中无 `IsRead` / `ReadAt` / `MarkRead` / 已读回执 | 需新增表/字段 + 回执端点 + 客户端上报 |
| **没有任何设备标识** | 代码库中无 `DeviceId` / 设备注册表 | B/C 方案需新增设备注册、标识持久化、失活设备清理 |
| 客户端取消息方式 | SignalR 直推 + `GetTopicMessagesAsync` 拉取 + `?after=` 增量补拉（S2-04/05）；Web 为 Blazor Server 电路（多标签 = 多电路，同一浏览器）；MAUI 为 Android / iOS / MacCatalyst / Windows | “设备”的边界需要定义：Web 的一个标签算一台设备还是一台浏览器算一台？ |
| 文本消息无详情页 | 文本直接渲染在列表气泡里 | “已读”不能定义为“打开详情”，只能定义为视口停留或显式操作 |
| 文件消息按需下载 | 用户点按才下载；服务端缩略图生成也会读文件 | 下载可作已读信号；缩略图生成必须排除在外，否则每条文件消息发出即焚 |
| FTS 索引（S3-03） | 行物理删除时触发器清 FTS 条目；标记 `DeleteAfter` 后、物理删除前的 7 天里，FTS 条目仍在，但读路径的 `NotExpired` 过滤使其不可见 | 已读焚复用标记路径时，搜索行为与定时销毁一致，无需额外处理 |
| 发件箱（S2-05） | MAUI 发件箱存未发出的消息 | 未发出的消息不存在“已读”，焚只适用于已发送的消息 |

## 3. 各方案实现成本估算（单人）

估算口径与 fix plan 一致：只计实现 + 回归，不计 Elan 的真机验证时间。

### 3.1 A 方案：任一设备已读即焚 + 回退超时

| 工作 | 内容 | 估算 |
|---|---|---|
| 服务端 | `ShareItems` 加 `ReadAt` / `ReadByDeviceId`（或独立 `MessageReads` 表）+ 迁移；`POST /api/v1/messages/{id}/read`（幂等：重复上报不重复触发）；已读后复用标记路径（置 `DeleteAfter`、广播 `ShareItemsDeleted`、更新主题元数据） | 2–3 天 |
| 客户端上报 | Web + MAUI 列表：文本按“视口停留 N 秒”上报，文件按“点开/下载”上报；发送设备排除；离线时回执进发件箱式队列，联网后补报 | 3–5 天 |
| 回归 | 多设备矩阵（Web + Android 各一台）：一方读、另一方立即消失；离线读后上线补报；与 1 分钟清理扫的竞态（已读标记与过期标记同时发生）；缩略图生成不触发已读 | 2 天 |
| **合计** | | **约 1.5–2 周** |

### 3.2 B/C 方案：全读完才焚 / 按设备分别焚

在 A 的基础上追加：

| 工作 | 内容 | 估算 |
|---|---|---|
| 设备注册表 | `Devices` 表（设备 GUID、最后上线时间、平台）；登录/启动时注册；设备标识持久化（MAUI `Preferences`、Web `localStorage`）；失活设备清理策略（多久未上线算放弃？谁来定？） | 3–4 天 |
| 服务端判定 | “是否全部读完”查询 + 失活设备不计入的规则；C 方案另需每设备隐藏状态 | 2–3 天 |
| 客户端 | 注册 + 标识续期 + 多标签 Web 的设备归属（同一浏览器多标签算一台还多台） | 2–3 天 |
| 回归 | 设备丢失/重置/重装后的行为；失活清理误删在线设备的边界 | 2 天 |
| **合计（在 A 之上追加）** | | **约 1.5–2 周；A+B/C 全量约 3–4 周** |

### 3.3 为什么不推荐 B/C

- B 的正确性依赖“设备清单是完整的”——而清单永远不完整（关机、出售、重装
  的设备无法自证），最终只能靠回退超时兜底；兜底一加上，B 与 D1 无差别。
- C 要求客户端本地持久化消息并各自删除，但现在客户端没有本地消息库
  （列表每次从服务端拉），C 等于 B 加本地隐藏状态，成本更高、收益相同。
- 两者都要先回答“多久未上线算放弃这台设备”——这是个产品决策，不是技术
  决策，且没有标准答案。

## 4. 迁移成本（如果 D1 改选）

| 方案 | 内容 | 估算 |
|---|---|---|
| **祖父条款（推荐）** | 已有消息保持定时销毁（`ExpiresAt` 不动）；只有改选之后新发的消息走已读销毁 | ~0（只需在设置里注明分界点） |
| **全量转换** | 清空已有消息的 `ExpiresAt`，加已读追踪字段，给未读消息设一个回退过期（例如 7 天）；一次迁移 + 按 plan 规则在旧数据副本上做升级/回滚演练 | 0.5 天 + 演练 |
| **文案回切** | “定时销毁”改回“阅后即焚”，并向用户说明新旧两种消息并存期 | 0.5 天 |

## 5. 风险与边界情况

- **离线读**：设备离线时读了消息，回执要等联网后才补报；此期间其他设备
  仍能看到该消息。A 方案下这是可接受的延迟（最终一致），不是缺陷。
- **发送设备排除**：必须在服务端校验（不能只靠客户端自觉不上报），否则
  一个旧客户端就能把所有消息瞬间烧掉。
- **重复上报与竞态**：回执端点必须幂等；已读标记与 1 分钟清理扫可能同时
  命中同一条消息，两者都走“置 `DeleteAfter` + 广播”时不得重复广播或报错。
- **缩略图与搜索**：服务端缩略图生成、FTS 建索引时的文件读取都不是“已读”，
  必须排除；否则文件消息一发出就烧。
- **多标签 Web**：同一浏览器开两个标签，算一台设备还是两台？A 方案下无需
  区分（任一已读即焚）；B/C 方案下必须先定，否则无法判定“全部读完”。
- **隐私含义变化**：定时销毁是“时间到了就没了”；已读销毁是“服务端知道你
  读过”。后者新增了服务端可观测的阅读行为记录（`ReadAt` / `ReadByDeviceId`），
  自用单用户场景下无实际隐私增量，但语义上要意识到这一点。

## 6. 建议

1. **保持 D1。** 定时销毁已完整实现并经过三阶段回归；已读销毁的增量收益
   （消息在被读后提前消失，而非等到固定 deadline）不值得 1.5–2 周的投入。
2. **如果将来改选**：只做 A + 回退超时（回退时长沿用 `BurnAfterReadingMinutes`），
   按 §3.1 的清单实施；不做 B/C。
3. **改选前必须先定的决策点**（缺一不可，否则无法开工）：
   - “已读”的操作定义：文本按视口停留几秒？文件按下载还是按点开预览？
   - 发送设备排除规则：按设备标识，还是按“发送后 X 分钟内不计已读”？
   - 回退超时时长：沿用 `BurnAfterReadingMinutes` 还是单独设？
   - 是否接受服务端记录阅读行为（`ReadAt` / `ReadByDeviceId`）？
   - 旧消息按祖父条款还是全量转换？
